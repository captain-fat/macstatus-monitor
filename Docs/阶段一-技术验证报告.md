# MacStatus Monitor · 阶段一技术验证报告

> 目标：在写任何 UI 之前，先证明 CPU / GPU / Memory Pressure 三项数据能**真实、连续、低开销**地采到，
> 尤其是 Apple Silicon 上最难的 GPU 使用率。
>
> 本文所有数据均来自本机实测，探针源码在 `Tools/Probes/`，可直接复现（见第 8 节）。

---

## 0. 结论摘要

| 项目 | 结论 | 依据 |
|---|---|---|
| CPU 采集 | **可行，推荐 `host_processor_info` 差值法** | 10 线程满载时每核 99–100%，与 `yes` 进程外部对照一致；单次采样 0.004–0.008 ms |
| GPU 采集 | **可行，推荐 IOReport 的 Active/Idle Time 直方图** | 用可控 Metal 占空比做真值，忙占比随之近似线性变化（见 3.3）<br>⚠️ 阶段三修正：1 Hz 下持续满载会让该直方图窗口塌缩，最终改用 `GPU Performance States` 状态驻留，见阶段三文档第 3 节 |
| GPU 备用 | `IOAccelerator.PerformanceStatistics["Device Utilization %"]` | 免 root、免私有框架，但高负载段严重压缩，只作降级方案 |
| GPU 若不可用 | 显示 **N/A**，绝不模拟 | 两条路径都失败时返回 nil，UI 显示 N/A 并在 Popover 说明原因 |
| Memory Pressure | **可行，`DispatchSource` 事件 + `sysctl` 初值** | 启动即可读到 Normal；warn/critical 事件需 root 模拟，已给出手动验证步骤 |
| 权限 | **不需要 root、不需要特殊授权、不需要 entitlement** | 全部以普通用户身份验证通过 |
| 资源占用 | 1 Hz 下自身 CPU **0.36%**（单核占比）、RSS 稳定在 **~12 MB** | 150 秒长跑，无增长趋势 |
| 私有 API 风险 | **存在且明确**：IOReport 是无公开头文件的私有框架 | SDK 中不存在 IOReport 头文件；发布策略见 3.6 |

**一句话结论**：GPU 使用率可以拿到真实数据，并且有一个比"驱动自报百分比"更可靠的硬件时间戳口径；
但它有私有 API 的代价，需要接受"非 App Store 分发"这个前提。

## 1. 测试环境与方法

| 项 | 值 |
|---|---|
| 机器 | MacBook Air `Mac17,4`（Apple M5，10 核：4P+6E，GPU 10 核） |
| 内存 | 32 GB |
| 系统 | macOS 27.2.1（26B131） |
| 工具链 | Xcode 27.2 / Swift 6.4.2，部署目标 macOS 14 |
| 身份 | 普通用户（`sudo` 在本环境不可用，也就顺带证明了**不需要 root**） |

方法：写一个独立的命令行探针 `probe`（`Tools/Probes`），包含：

1. 三套采集实现（CPU / GPU 多方案 / Memory Pressure）；
2. 一个 **Metal 负载发生器**，可以按"忙 N ms / 闲 M ms"的节奏制造**已知占空比**的 GPU 负载；
3. 一个**占空比矩阵**实验：对 0/20/40/60/80/100% 六档真值，同时记录每个候选指标的读数；
4. 一个 1 Hz 长跑，观察自身 CPU 与 RSS。

"真值"从哪来：Metal 的 `waitUntilCompleted` 能精确知道 GPU 繁忙区间，因此"我们自己的忙闲比"是已知量；
再叠加系统背景 GPU 活动，就得到一组**单调、可解释**的对照曲线。这比"看起来像"要可靠得多。

## 2. CPU 采集：验证通过

### 2.1 方案

`host_processor_info(host, PROCESSOR_CPU_LOAD_INFO)` 返回每核 4 个 tick 计数：
`CPU_STATE_USER / SYSTEM / IDLE / NICE`（32 位，会回绕）。用相邻两次采样的差值算比例：

```
usage_core = (Δuser + Δsystem + Δnice) / (Δuser + Δsystem + Δnice + Δidle)
usage_total = ΣΔbusy / ΣΔtotal
```

实现要点（已写进探针，阶段三直接复用）：

- `mach_host_self()` 只取一次，`deinit` 里 `mach_port_deallocate`，否则每次采样泄漏一个 send right；
- `host_processor_info` 返回的内核内存必须 `vm_deallocate`，否则 1 Hz 跑几小时就是持续泄漏；
- 首次采样没有基准 → 返回 `nil`，UI 显示占位符，而不是显示一个假的 0%；
- 32 位计数回绕用无符号减法（`&-`）天然正确；
- 同时保留 user/system/idle 分量，供 Popover 详情展示。

### 2.2 实测

| 场景 | 总 CPU | 每核 |
|---|---|---|
| 空闲（系统自身有 30% 左右背景负载） | 32–38% | 前 6 核 ~55%，后 4 核 ~5% |
| 外部起 10 个 `yes` | **99.6%** | 99–100% ×10 |
| 探针内起 10 个忙等线程 | **98–100%** | 97–100% ×10 |
| 负载结束 | 35% | 回落 |

每核读数与 `ps`/`yes` 的外部对照一致，说明"区分多核、区分 user/system/idle"都成立。

### 2.3 开销

`host_processor_info` + 差值计算：**0.004–0.008 ms/次**，可忽略。

## 3. GPU 采集：重点验证

### 3.1 候选接口盘点（本机实测能否用）

| 方案 | 免 root | 数据性质 | 本机结论 |
|---|---|---|---|
| **A. IOReport `GPU Stats / Active Time Histogram` + `Idle Time Histogram`** | ✅ | 硬件 24 MHz 时间戳统计的**忙/闲时长** | **采用**：线性、可自校验 |
| B. IOReport `GPU Stats / GPU Performance States`（OFF,P1…P15） | ✅ | **频率/功耗状态**驻留，不是利用率 | 仅作诊断，不作显示 |
| C. IOReport `GPU Stats / UT Engagement centi-% Histogram` | ✅ | 利用率直方图（0–10000 百分之一百分比） | **实测失效**：恒定 0.25–0.31%，与负载无关 |
| D. IOAccelerator `PerformanceStatistics["Device Utilization %"]` | ✅ | 驱动自报百分比 | **降级备用**：低段准、高段饱和 |
| E. `powermetrics --samplers gpu_power` | ❌ 需 root | 官方口径 | 不可用（本环境无 sudo） |
| F. Metal 计数器 / GPUTools | 需开发者工具 | 精确但侵入 | 不适合常驻工具 |

> 表中 A/C/D 三个 IOReport 频道都在同一个 group（`GPU Stats`）里，一次订阅即可全部拿到，共 **133 个频道**。

### 3.2 IOReport 接入方式（踩过的坑）

1. **路径**：macOS 26/27 已经**没有** `IOReport.framework` 目录，框架只在 dyld 共享缓存里；
   用 `dlopen("/usr/lib/libIOReport.dylib")` 可以拿到。老系统（14/15）通常在
   `/System/Library/PrivateFrameworks/IOReport.framework/IOReport`。两条路径都要留。
2. **符号**：全部 `dlsym` 动态绑定，不写进 LC_LOAD_DYLIB，缺符号时降级而不是崩溃。
   需要的符号：`IOReportCopyChannelsInGroup / IOReportCreateSubscription / IOReportCreateSamples /
   IOReportCreateSamplesDelta / IOReportChannelGetGroup|SubGroup|ChannelName|Format|UnitLabel /
   IOReportSimpleGetIntegerValue / IOReportStateGetCount|NameForIndex|Residency /
   IOReportHistogramGetBucketCount|BucketMinValue|BucketMaxValue|BucketHits`。
3. **内存所有权**：`Copy*/Create*` 返回 **+1**，`ChannelGet*` / `StateGet*` 返回 **+0**。
   最初对 `IOReportChannelGetGroup` 用了 `takeRetainedValue`，直接段错误——这类错误在 UI 里会表现为偶发闪退，必须一开始就写对。
4. **样本结构**：不是"group → subgroup → channel"三层字典，而是
   `{"IOReportChannels": [channelDict, ...]}`，每个 `channelDict` 带 `RawElements`(CFData) 元数据。
   判断"是不是频道"最稳的标记是存在 `RawElements`。
5. **format 枚举**（实测）：`1 = simple`、`2 = state`、`3 = histogram`。
   对 state 频道调 `SimpleGetIntegerValue` 会得到 `INT64_MIN` 这类垃圾值，绝不能混用。

### 3.3 占空比矩阵实验（核心证据）

Metal compute 每次 dispatch 约 100–117 ms，按目标占空比插入空闲。每档跑 8 秒，每 250 ms 采一次样。
"实测"列是负载线程自己统计的真实占空比。

**第一轮**（含 UT 直方图、非 OFF 驻留、GPU 能量）：

| 目标 | 实测 | IOAcc % | 非 OFF % | UT 均值 % | GPU 能量/s |
|---:|---:|---:|---:|---:|---:|
| 0% | 0.0% | 48.2 | 50.8 | 0.25 | 1.39e8 |
| 20% | 30.3% | 68.9 | 54.3 | 0.29 | 6.23e8 |
| 40% | 44.9% | 87.2 | 64.9 | 0.29 | 1.35e9 |
| 60% | 64.1% | 92.8 | 79.2 | 0.30 | 1.81e9 |
| 80% | 82.7% | 95.1 | 89.6 | 0.29 | 2.22e9 |
| 100% | 100.0% | 99.3 | 99.2 | 0.29 | 2.66e9 |

**第二轮**（加入 Active/Idle Time 忙占比，背景 GPU 活动较少，故 0% 基线从 48% 降到 29%）：

| 目标 | 实测 | IOAcc % | **忙占比 %** | 非 OFF % | GPU 能量/s |
|---:|---:|---:|---:|---:|---:|
| 0% | 0.0% | 30.3 | **29.0** | 29.7 | 5.5e7 |
| 20% | 30.9% | 67.4 | **46.5** | 51.1 | 5.2e8 |
| 40% | 44.2% | 84.6 | **59.8** | 61.6 | 1.28e9 |
| 60% | 63.7% | 93.8 | **75.5** | 77.0 | 1.79e9 |
| 80% | 82.4% | 94.7 | **87.6** | 88.1 | 2.19e9 |
| 100% | 100.0% | 98.9 | **94.0** | 99.5 | 2.72e9 |

**怎么读这张表：**

- **GPU 能量从 5.5e7 涨到 2.7e9（约 50 倍）**——证明这套 Metal 负载是真打在 GPU 上，
  读数变化不是噪声，也不是 CPU 副作用。
- **UT 直方图恒定在 0.29%**——它在本机（M5 / macOS 27）不随负载变化，直接淘汰。这就是"看起来最像利用率"的接口反而不能用。
- **IOAcc 严重饱和**：40%→100% 真值只从 84.6 涨到 98.9，中间 60% 与 80% 只差 0.9 个点。
  做进度条会"一过 50% 就贴顶"，用户无法区分中等负载和满负载。
- **忙占比近似线性**：以"背景活动 + 负载"模型拟合，`忙占比 ≈ 基线 + 0.66 × 实测占空比`，
  基线就是 0% 档的 29%。6 个点的偏差都在 ±5 个点内。
- **非 OFF 驻留**趋势类似但更粗：它把 P1（最低频）也算"非 OFF"，而 P1 下 GPU 几乎不干活，
  所以它会把空闲基线抬高（第一轮 50.8%），不适合当利用率。

**为什么 0% 档不是 0？**
GPU 只有"完全没有工作"时才进入 idle。桌面合成（WindowServer）、浏览器动画等后台绘制本身就会周期性
唤醒 GPU，本机实测能占到 29%–52%（取决于屏幕上有多少东西在动）。因此有负载时：

```
忙占比 = 占空比 + (1 − 占空比) × 基线 = 基线 + (1 − 基线) × 占空比
```

拟合斜率 `1 − 0.29 = 0.71`，与实测斜率 0.66 基本一致，剩下的差异来自背景下限本身的波动。

### 3.4 选定口径与公式

采用 `GPU Stats` 下两个直方图频道：

| 频道 | subgroup | name | format | unit |
|---|---|---|---|---|
| GPU Active Time | `Active Time Histogram` | `GPU Active Time` | 3 (histogram) | `24Mticks` |
| GPU Idle Time | `Idle Time Histogram` | `GPU Idle Time` | 3 (histogram) | `24Mticks` |

对 delta 后的直方图：

```
activeSeconds = Σ_hits × (bucketMin + bucketMax) / 2 / 24e6
idleSeconds   = 同理
utilization   = activeSeconds / (activeSeconds + idleSeconds) × 100
```

**自校验**（很重要，用来防"数据源坏了还照显示"）：

- `activeSeconds + idleSeconds` 应约等于采样窗口（1 s 时实测 0.504 + 0.502 ≈ 1.006 s）；
- 若偏差超过 ±30%，说明该窗口数据不完整（例如 GPU 深睡、订阅刚建立），标记为不可信；
- 有效桶数、命中数为 0 时返回 nil → UI 显示 N/A。

单次"活跃区间"均值也能顺带算出来（本机空闲时 ~5.9 ms/次，与 120 Hz 屏幕刷新节奏吻合），
可作为将来"GPU 活动频率"的细节展示。

### 3.5 备用与降级链

```
IOReport Active/Idle Time  ──成功──▶ 忙占比
        │失败/不可信
        ▼
IOAccelerator "Device Utilization %" ──成功──▶ 该百分比（标注"驱动口径"）
        │失败
        ▼
        N/A（Popover 里说明"当前系统/芯片不支持"）
```

`IOAccelerator` 路径实现极简单：`IOServiceMatching("IOAccelerator")` → 读
`PerformanceStatistics` 字典 → `Device Utilization %`（本机为 `AGXAcceleratorG17G`），
单次 0.017–0.021 ms，免 root。它的缺点是 3.3 里看到的饱和，所以只做降级。

### 3.6 私有 API 风险评估（必须让用户知情）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 非公开接口 | SDK 中**不存在** IOReport 头文件；频道名/枚举可能随系统版本变化 | 动态绑定 + 每次启动做能力探测 + 失败降级 N/A；把实现隔离在 `IOReportGPUSampler` 一个文件里 |
| App Store | 使用私有 API 的应用**大概率被拒** | 定位为 Developer ID / 本地签名分发；若要走 App Store，需去掉 GPU 真实值改为 N/A 或仅保留 IOAcc |
| App Sandbox | 本机验证的是非沙盒进程；沙盒下 IOReport/IOKit 是否可用**未验证** | 阶段二先用非沙盒签名验证；如必须沙盒，需单独做一次沙盒实验 |
| 系统升级 | 频道名、单位（`24Mticks`）可能变 | 单位解析写成通用函数（支持 `GHz/MHz/kHz/ticks`），并把"窗口自校验"作为运行期保险 |
| 硬件差异 | 只在 M5 上验证；M1–M4 未测 | 阶段五做多机验证清单；代码里对"频道缺失"完全容错 |

### 3.7 一个必须提前说清的产品事实

**"GPU 使用率"不是只有本应用在用时才涨。** 空闲桌面上（有 120 Hz 屏幕 + 浏览器窗口），
本机实测 GPU 忙占比在 **29%–52%** 之间波动，取决于屏幕上有多少东西在动；
等界面完全静止后才掉到 **5%–8%**（见第 5 节长跑数据）。

这意味着：

- 菜单栏的 GPU 条在"用户什么都没干"时也可能是 30%，这不是 bug，是系统口径（驱动自报值在同一时刻也是 30–48%，
  说明这是系统口径，不是本应用的口径偏差）；
- 因此**不能用"空闲应为 0%"来验收**，验收标准应是：与 Activity Monitor/驱动口径同量级、
  对负载单调、无跳变、无随机数。

## 4. Memory Pressure：机制验证通过，事件触发待手动补测

### 4.1 方案（两条独立通道）

1. **初值**：`sysctl kern.memorystatus_vm_pressure_level`
   （XNU 定义：1 = Normal，2 = Warning，4 = Critical）。DispatchSource 只在**变化**时回调，
   启动瞬间不会给值，所以必须用 sysctl 补初值。
2. **变化**：`DispatchSource.makeMemoryPressureSource(eventMask: [.normal, .warning, .critical])`，
   事件驱动、零轮询。`.critical` 优先级最高，其次 `.warning`，最后 `.normal`（恢复）。

**明确不做**：不用"已用内存百分比"、不用"free 低于 X%"来推导压力等级。

### 4.2 本机实测

```
启动时: raw=1 level=Normal
总内存 34.4 GB, free 0.17 GB, compressor 6.21 GB, wired 4.02 GB, swap used 2.82 GB
[事件] 初始状态 -> Normal
```

注意这组数字本身就是"不能用剩余内存代替压力"的最好证据：
**free 只剩 0.17 GB（0.5%），但系统压力等级是 Normal**。macOS 会主动把内存用在缓存/压缩上，
剩余内存少是常态，与压力无关。

### 4.3 为什么没测到 Warning / Critical

模拟压力需要 root：

```
$ memory_pressure -S -l warn -s 5
sysctl: kern.memorypressure_manual_trigger failed : Operation not permitted
```

本环境 `sudo` 不可用（沙盒限制），也不应为了测试去真实吃满 32 GB 内存（会让整机卡死、触发大量 swap）。
因此 **DispatchSource 的 warn/critical 通路只完成了代码级与初始态验证，端到端事件未实测**。

请在阶段二用你自己的终端跑这两条命令补测（约 20 秒，系统会自动恢复）：

```bash
# 终端 A：跑一个监听程序（阶段二会做成 app 的一个 --debug 模式）
# 终端 B：
sudo memory_pressure -S -l warn -s 10      # 应看到 Warning（黄框）
sudo memory_pressure -S -l critical -s 10  # 应看到 Critical（红框），结束后回到 Normal
```

如果这两条不通，退路是：用 `sysctl` 以 1–2 秒节奏轮询等级（开销 0.002 ms，可忽略），
依然**不用**已用内存比例。

## 5. 性能与资源占用（1 Hz 长跑 150 秒）

| 指标 | 结果 |
|---|---|
| 自身 CPU | 0.27–0.39%，平均 **0.36%**（单核占比，即整机约 0.04%） |
| RSS | 9.7 MB → 12.1 MB 后**平台化**，无持续增长 |
| 单帧耗时 | 2.2–4.0 ms（含三路采样 + 格式化输出） |
| 累计 CPU | 151 秒共 0.544 s |

长跑中的 GPU 读数变化（同一次运行）：

```
10:06:41  CPU 29.5%  GPU忙 48.5%  IOAcc 46.0%   ← 屏幕上有动画/合成活动
...
10:07:51  CPU 51.8%  GPU忙 47.7%  IOAcc 42.0%
10:08:01  CPU 39.8%  GPU忙  8.3%  IOAcc  0.0%   ← 界面静止，GPU 真正空闲
10:08:51  CPU 35.9%  GPU忙  8.0%  IOAcc  0.0%
```

这段数据同时说明两件事：
1. 两个独立数据源在"真空闲"时一致（8% vs 0%，都接近 0），在"低负载"时也一致（48% vs 46%）；
2. 它们在"高负载"时分离（见 3.3），所以选硬件时间口径，而不是驱动百分比。

### 单次采样成本（微基准，30 次平均）

| 操作 | 耗时 |
|---|---|
| IOReport 整组 `sample + delta` | 0.553 ms |
| 整组 + 解析 133 个频道 | 0.612 ms |
| **双过滤订阅（Active + Idle）`sample + delta`** | **0.164 ms** |
| 单过滤订阅（Active） | 0.098 ms |
| IOAccelerator 读 `PerformanceStatistics` | 0.021 ms |
| CPU `host_processor_info` + 差值 | 0.008 ms |
| 内存压力 sysctl + `vm_statistics64` | 0.002 ms |

结论：正式实现用**两个过滤订阅**（只订 `Active Time Histogram` 和 `Idle Time Histogram`），
单帧总成本预计 ≈ 0.2–0.5 ms；1 Hz 下自身 CPU 预计从 0.36% 降到 **0.1% 以内**（阶段三实测确认）。

```
│   └── SystemMonitor         单一 1 Hz 循环，产出 MonitorSnapshot
├── AppKit 层
│   ├── MenuBarController     NSStatusItem + 自定义 NSView（Core Graphics 绘制）
│   └── StatusBarView         两个圆角条 + 包裹式压力外框
└── SwiftUI 层
    ├── MonitorPopover        详情（每核、user/system/idle、GPU 来源、内存明细）
    └── SettingsView          刷新间隔/数字开关/三色选择/开机启动
```

关键约束（写进代码规范）：

- 采集层不 import SwiftUI/AppKit；
- `SystemMonitor` 只有**一个**定时源（`DispatchSourceTimer` 或一个 `Task` 循环），
  不允许每个模块各起一个 Timer；
- 只有"值变化超过阈值"（例如 1%）才写回 UI 状态，避免每秒重绘两次；
- 停止时显式 `cancel()`、释放 IOReport 订阅、`vm_deallocate`，并用长跑验证 RSS 不涨。

### 6.2 菜单栏布局（草案）

```
┌──────────────────────────────────────────────────────────┐
│  CPU ▰▰▰▰▰▱▱▱  42%   GPU ▰▰▰▱▱▱▱▱  31%   ╭────────╮      │
│                                          │ Normal │      │
│                                          ╰────────╯      │
└──────────────────────────────────────────────────────────┘
```

- 两个条各 ~34 pt 宽、5 pt 高、2.5 pt 圆角，用 `NSBezierPath` 直接画（比 SwiftUI hosting 更省、更锐利）；
- CPU 蓝 `systemBlue`、GPU 紫 `systemPurple`（自动适配深浅色）；
- 压力是**包住 CPU/GPU 两行的彩色圆角外框**（不是进度条、无文字）；绿/黄/红分别用 `systemGreen/systemYellow/systemRed`；
- 实测宽度（阶段二落地）：显示百分比 **93 pt**，两个百分比都关掉 **65 pt**；
- 数字用等宽数字（`monospacedDigitSystemFont`），避免百分比位数变化导致抖动；
- 点击弹 Popover（`NSPopover` + `NSHostingController`），不做独立窗口。

### 6.3 刷新与防闪烁

- 默认 1 s，可选 0.5 / 1 / 2 / 5 s；按 0.2–0.5 ms/帧估算，0.5 s 刷新仍远低于 0.5% CPU；
- CPU/GPU 用 1 s 窗口的**差值**，天然平滑；再叠一个 3 帧的指数滑动平均（α≈0.35）消除抖动；
- 进度条宽度变化用 `CATransaction` 关掉隐式动画，或直接重绘（小视图重绘成本远低于动画掉帧）；
- 压力外框只在等级变化时换色，不跟随数值跳动。

## 7. 已知限制 / 需要在阶段二确认的问题

1. **GPU 语义**：忙占比包含 WindowServer 合成，空闲 5%–50% 取决于屏幕内容；文案上建议叫 "GPU" 并在
   Popover 注明"含系统合成，口径为硬件忙时占比"。
2. **高负载段与 Activity Monitor 不一致**：我们的 94% 对应它的 ~99%。验收时以"单调、可解释"为准。
3. **IOReport 沙盒可用性未测**：若你要求 App Store 或沙盒分发，需要先做一次沙盒实验，可能要退回 IOAcc/N/A。
4. **warn/critical 端到端未测**：需要你用 sudo 跑第 4.3 节两条命令。
5. **只在 M5 + macOS 27 验证**：M1–M4、macOS 14/15 的频道可用性需要在阶段五补测（代码已做缺失容错）。
6. **开机启动**：macOS 13+ 用 `SMAppService.mainApp.register()`，需要签名的 .app 放在 /Applications 才稳定；
   未签名时该开关会失败，UI 要给出明确提示而不是静默失败。

## 8. 如何复现（探针）

```bash
cd Tools/Probes
./build.sh                 # 直接用 swiftc 编译，约 3–4 秒，产物 .build/bin/probe

./.build/bin/probe explore-gpu     # 枚举 IOReport 频道 + IOAcc 全部键值
./.build/bin/probe matrix 8        # 六档占空比对照实验（约 60 秒）
./.build/bin/probe soak 150        # 1 Hz 长跑，每 10 秒打印自身 CPU / RSS
./.build/bin/probe bench           # 各采集路径的微基准
./.build/bin/probe cputest 10      # CPU 采样 vs 自造满载
./.build/bin/probe mempressure 20  # 内存压力监听（配合第 4.3 节 sudo 命令）
```

> 注：本机沙盒环境下 SwiftPM 无法写 `~/Library` 缓存，所以 `build.sh` 绕开 SwiftPM 直接调用 `swiftc`。
> 你在正常终端里用 `swift build` 也可以。

探针源码（也是阶段三要抽成 `MonitorKit` 的雏形）：

| 文件 | 作用 |
|---|---|
| `CPUSampler.swift` | Mach host 统计 + 差值 |
| `MemoryPressureSampler.swift` | DispatchSource + sysctl + vm_statistics64 |
| `IOAcceleratorGPUSampler.swift` | 降级方案 |
| `IOReportBridge.swift` | IOReport 动态绑定、订阅、频道遍历、直方图解码 |
| `GPUUtilization.swift` | 忙占比 / 状态驻留 / 直方图等口径 |
| `GPULoadGenerator.swift` | Metal 可控负载（仅测试用） |
| `Matrix.swift` / `Soak.swift` / `Bench.swift` | 三组验证实验 |
